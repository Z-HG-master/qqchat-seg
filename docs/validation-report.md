> 目的：验证「群聊数据清洗」流程中**算法机制是否成立**，以及在同类任务上处于什么水平。
> 原则：测试只用于**验证**，不用于**调参**。任何“为提分改判据”的做法都被明确排除（否则就是考试模型）。
> 数据目录：`bench/data/`（不在仓库内）　脚本：`bench/`

## 2. Ubuntu IRC：主基准（最贴近目标场景）

### 2.1 为什么选它

数据集的正式名字是 **Conversation Disentanglement（会话解缠）**——它存在的唯一原因就是
多条对话在同频道交织。实测：

```
滑动 20 条窗口内存在多个对话串的比例：100.0%
回复距离分布：1条前71次 / 2条前49 / 3条前22 / … / 15条前1次
```

**交织程度比 QQ 群更严重。**

### 2.2 任务适配

```
原始任务：最后一条消息在回复窗口里哪一条（回复自己 = 开新串）
我们的适配：目标消息 → 判「续 / 新」
金标「新」= parents 指向自身 = 19.3%
```

### 2.3 边界判定结果

| 模型 | P | R | **F1** | 准确率 | 耗时 | 单样本 |
|---|---|---|---|---|---|---|
| **`qwen/qwen3.5-9b@q4_k_m`** | **0.893** | 0.833 | **0.862** | **94.9%** | 7.5 min | 188 ms |
| `qwen/qwen3.8-27b@q4_k_m` | 0.688 | **0.972** | 0.805 | 90.9% | 55.3 min\* | 1384 ms |
| 9B + 27B 复核（1.3 阶段，10 通道） | 0.781 | 0.841 | 0.810 | — | 7.3 min | — |
| 全判“续”基线 | — | 0 | 0 | 80.7% | — | — |

**9B 单步是最优配置：分数最高且最快。27B 召回极高（0.970）但精确率崩（0.695）。**

> 后续文中为简洁起见：**9B** = `qwen/qwen3.5-9b`，**27B** = `qwen/qwen3.8-27b`，
> 两者均为 Q4_K_M 量化 + 视觉能力，设备与加载参数见 §0。

### 2.4 错误构成分析（小模型，123 个错误）

| 类型 | 数量 | 占比 | 典型样本 |
|---|---|---|---|
| **FN 该切没切** | **77** | 63% | `ask! problem with ndiswrapper with broadcom wlan chipset`<br>`I have a question about installation...` |
| **FP 不该切硬切** | **46** | 37% | 系统消息（进出群）、`Hallo all`、机器人发言 |

> 计数对应 §2.7 的新措辞重测；具体成因抽样基于旧措辞的预测，类型分布形状未变。

**发现：**

- **FN 主因**：新人提出全新问题。语义上仍属“Ubuntu 技术支持”，但结构上是新对话串。
- **FP 主因（约 15–20 个）**：标注口径差异——系统消息/打招呼在 IRC 标注里算“续”，
  语义上确实无关。**这部分不是算法错误。**

**⚠️ 重要**：这两类成因**不能用于改判据**——IRC 的“新”是结构定义，QQ 群的“新”是语义定义。

### 2.5 1.2 非连续合并验证

**指标**：pairwise F1（任取两条消息，是否属于同一对话串）

| 策略 | P | R | pairwise F1 |
|---|---|---|---|
| 全判“不同串” | — | 0 | 0.000 |
| 全判“同一串” | 0.056 | 1.000 | 0.107 |
| 纯连续切分（仅 1.1） | 0.403 | 0.322 | 0.348 |
| **+ 1.2 非连续合并** | 0.358 | **0.413** | **0.373** |

> 同串消息对仅占 **5.63%**（16,117 / 286,210），指标天然严苛。

**10/10 通道全部正收益**，事件数平均减少 30–50%。

**0.7 初审在 IRC 上确认率 97.1%（1,767/1,819）**——几乎不过滤任何链接，
该环节在此数据集上“空转”。

### 2.6 规模上限扫描（重要发现）

| 上限 | P | R | pairwise F1 | 相对纯连续 |
|---|---|---|---|---|
| **无上限** | 0.130 | 0.971 | **0.222** | **−12.6** ❌ |
| **≤20 条 / ≤2000 字** | 0.358 | 0.413 | **0.373** | **+2.5** ✅ |
| ≤50 条 / ≤5000 字 | 0.254 | 0.704 | 0.366 | +1.8 |
| ≤100 条 / ≤10000 字 | 0.181 | 0.876 | 0.294 | −5.4 ❌ |
| ≤200 条 / ≤20000 字 | 0.136 | 0.953 | 0.231 | −11.7 ❌ |

**结论：并查集传递闭包是本算法的固有风险，必须有规模上限。**

无上限时召回 0.970 但精确率仅 0.136——一条回复链能把整条通道焊成一坨
（在真实群数据上曾出现过 722 unit / 24,376 字的巨块）。

**⚠️ 说明**：该上限是**实现者自定的参数**，非原始需求。在 QQ 数据上
**未做过同款扫描**，当前值 20/2000 未经证实。

### 2.7 提示词措辞修订：从「QQ 群」到「社交群聊」

**背景**：本项目定位已泛化为「社交群聊」工具（支持 ChatLab 格式的 WhatsApp / Discord /
Telegram 等），但提示词原文写的是「QQ 群」。为验证措辞改动是否影响切分质量，
把 6 条提示词里的「QQ 群」统一替换为「社交群聊」，其余一字未改，并在同一环境下重测。

| 指标 | 旧措辞（QQ 群） | 新措辞（社交群聊） | 差异 |
|---|---|---|---|
| 9B 单步 F1 | 0.870 | **0.862** | −0.008 |
| 9B 单步 P / R | 0.878 / 0.862 | 0.893 / 0.833 | +0.015 / −0.029 |
| 9B 准确率 | 95.0% | 94.9% | −0.1pp |
| 27B 单步 F1 | 0.809 | **0.805** | −0.004 |
| 9B+27B 复核 F1 | 0.833 | 0.810 | −0.023 |
| pairwise 合并前 → 后 | 0.345 → 0.377 | 0.348 → 0.373 | 同向 |
| 无上限对照 | 0.232 | 0.222 | 同向（结论不变） |

**结论**：措辞中立化带来 **0.4–0.8 个百分点的 F1 小幅下降**，方向一致但不改变任何结论
（9B 仍优于 27B 单步、复核仍降分、合并仍提升、无上限仍崩）。

**为什么不是噪声**：同一措辞连续跑两次，混淆矩阵**逐位相同**
（TP=385 FP=46 FN=77 TN=1889），说明 `temperature=0.0` 下结果是确定性的；
0.008 的差异来自措辞本身的语义影响，而不是采样抖动。

**取舍**：0.8% 的 F1 换「可跨平台使用」的定位，我们认为值得。
需要旧措辞的数字时，可用 `--prompts-override` 换回（见 `core/prompts.py`）。

> \* 27B 本次重测时 9B 同时驻留显存（共 29.3 GB / 32.6 GB），速度受挤占（1.38 s/样本）；
> 单独加载时约 0.66 s/样本。F1 不受影响。

## 3. TIAGE：双人闲聊（体裁不匹配对照）

| 方法 | F1 |
|---|---|
| **我们的大模型（27B 量级）** | **0.391** |
| CSM（专门训练） | 0.427 |
| BayesSeg | 0.366 |
| **ChatGPT 零样本** | **0.362** |
| InstructGPT | 0.280 |
| **我们的 `qwen/qwen3.5-9b@q4_k_m`** | **0.279** |
| TextTiling | 0.204 |
| Random | 0.237 |

**观察：**

- 大模型**超过 ChatGPT 零样本**（0.391 vs 0.362），距专门训练的 CSM 仅差 0.036；
- 小模型与 InstructGPT 持平；
- **小模型 + 大模型复核反而更差**（0.249 → 0.239）：复核新增 37 个边界，仅 2 个正确。

**局限**：英文、对话本身语义断裂、TIAGE 标注 Kappa 仅 0.479。

| 会议 | 句数 | 金标边界 | P | R | F1 |
|---|---|---|---|---|---|
| M0115 | 1,181 | 17 | 0.091 | 0.059 | 0.071 |

## 5. 图片转述（2.1）测试

### 5.1 提示词迭代（20 张图，大模型，两行格式）

| 版本 | 平均字数 | 超 80 字 | **意图命中** | 人名 | 引对话 | 元叙述 |
|---|---|---|---|---|---|---|
| v1 禁上下文 | 55.0 | 1 | 1/20 | 0 | 1 | 0 |
| v2 ②加强 | 55.0 | 1 | 1/20 | 0 | 1 | 0 |
| v3 允许“相关推理” | 59.5 | 2 | 4/20 | 0 | 1 | 0 |
| **v4 全加「描述」前缀（定稿）** | **57.0** | **1** | **6/20** | **0** | **1** | **0** |

**经验**：给每条要求加「描述」/「关联」前缀限定，模型不再纠结约束对象，
意图命中率从 4/20 提到 6/20。

### 5.2 单行 vs 两行（8 张，大模型）

| 配置 | 字数 | 意图 | 引对话 | 单张耗时 | 815 张耗时 |
|---|---|---|---|---|---|
| A 单行 + 思考(minimal) | 68.2 | 4/8 | **1** | 6.39s | ~87 min |
| **B 两行 + 不思考** | 49.5 | **4/8** | **0** | **1.49s** | **~20 min** |
| C 单行 + 不思考 | 66.5 | 4/8 | 0 | 1.18s | ~16 min |

**结论：「让模型多写一行」与「让模型多想一会儿」效果等价（都是 4/8），
但后者贵 4.3 倍且引入污染。**

### 5.3 小模型 vs 大模型图片精判（20 张）

| 指标 | 小模型 | 大模型 |
|---|---|---|
| 平均字数 | 48.2 | 55.1 |
| 超 70 字 | 2/20 | 4/20 |
| 含发言人名 | 0/20 | 0/20 |
| 引对话原句 | 1/20（实为图上文字，误判） | 1/20 |
| 元叙述 | 0/20 | 0/20 |
| 单张耗时 | 0.69s | 1.47s |

**语义审计（人工看图核对 3 例）：小模型 2 胜 1 负。** 大模型有时“多抓细节”实为编造
（把对话内容说成图上的）。

### 5.4 OCR 注入实验（6 张图，大模型 + OCR）

| 组 | OCR 事实命中率 |
|---|---|
| A 不加 OCR | **21/38 = 55.3%** |
| B 注入 OCR 文本 | 20/38 = **52.6%** |

**无提升，且引入了新的错误归属。**
**原因**：80 字上限卡死信息量；OCR 有错字噪音；大模型视觉本身够强。

### 5.5 大模型 vs 专用 OCR 识别能力

| 维度 | 胜者 |
|---|---|
| 中文手写/游戏字体 | **大模型** |
| 英文艺术字 | **大模型** |
| 密集小字覆盖量 | 专用 OCR |
| 速度 | 专用 OCR |
| 确定性 | 专用 OCR |

**结论：不必引入专用 OCR 做注入；OCR 仅适合做独立的“原始文本层”存档。**

## 6. 思考模式实测（特定模型家族行为，非项目前提）

### 6.1 参数是否可控

固定短输入、每组 3 次（大模型）：

| 设置 | reasoning tokens |
|---|---|
| 不传 | 95–97 |
| none | **0** |
| minimal | 79–86 |
| low | 85–122 |
| medium | 105–126 |
| high | 114–133 |
| `thinking_budget=128` | 忽略（同 high） |
| `max_thinking_tokens=128` | 忽略 |

**有响应但幅度小（1.5 倍）；`thinking_budget` / `max_thinking_tokens` 完全无效。**

**小模型完全不响应**：minimal / high 思考量一致（1,847–3,082 字），只有 `none` 能关闭。

⚠️ 这是**特定模型家族**的实测行为，不是所有 OpenAI 兼容模型的通用规律。
**本项目不依赖思考模式**：配置里默认不发送 `reasoning_effort`；需要模型「多想一步」时，
用的是提示词层面的「判定 + 一句理由」，成本只有几十个输出 token（见 1.1 的设计）。
如果你用的模型默认开思考且拖慢速度，可在 config.json 里显式关掉（可选）。

### 6.2 长输入上的表现

| 设置 | reasoning 字数 | 耗时 |
|---|---|---|
| none | 0 | 0.9s |
| **minimal** | **557** | **5.0s** |
| 不传 | **4,402** | **31.8s** |

**`minimal` 能把思考压到默认的 1/8——这是本次研究中唯一“可用”的思考档位。**

### 6.3 对两个任务的影响（大模型）

| 任务 | none | minimal | low |
|---|---|---|---|
| **图片精判** | 1.6s / 意图 1/6 | 6.6s / **意图 5/6** | 6.9s / 意图 5/6 |
| **长事件判读** | 1.5s | 9.0s（5 个里 4 个相同） | 9.8s |

**思考对图片精判的“意图命中”有显著提升（1/6→5/6），对分段判读几乎无益。**

**但由于两行格式已能达到同样效果（见 §5.2），生产上仍选择不思考。**

## 7. 未验证部分

### 7.1 图文事件归属（核心功能缺口）

**现状**：没有任何公开数据集标注了“图属于哪个事件”。
最接近的是**图文互选（Image Retrieval）**任务（PhotoChat / DialogCC / MMDialog），但：

```
PhotoChat 原始图片链接抽样 8/8 全部失效（HTTPError/超时）
镜像站数据集服务在本机不可达
```

**已设计但未执行的测试方案**：

```
方案 A（零外部依赖，推荐）：
  抽 100 张我们自己的图
  对每张构造 4 选 1：1 个真实事件上下文 + 3 个随机其他事件
  问模型“这段图片描述出自哪段对话？”
  准确率 25% = 描述完全通用（归属信息丢失）
  准确率 >90% = 描述高度事件特定（归属信息保留）

方案 B（图文配对合理性）：
  A 组真实配对 / B 组错配对
  问“这张图出现在这段对话里合理吗”
  比较两组“合理”比例
```

### 7.2 真实群聊数据（最关键的缺口）

| 缺失项 | 影响 |
|---|---|
| 人工标注的事件边界 | 无法给出真实场景的准确率 |
| 规模上限的最优值 | 当前 20/2000 未经扫描 |
| 质量闸门阈值 30 字 | 未经数据验证 |

**替代方案（无需人工）**：

| 指标 | 当前值 | 性质 |
|---|---|---|
| 结构边闭合率 | 73.1% | @/reply 协议字段当弱金标 |
| 稳定性（换参数重跑） | 93.5%（窗口版） | 衡量可复现性 |
| 消融 A/B/C/D | 未做 | 验证每步是否有正贡献 |

## 9. 方法论教训

| 教训 | 说明 |
|---|---|
| **测试不等于调参** | 曾提议“按 IRC 的结构定义改 1.1 判据”，属拟合测试集，已否决 |
| **体裁不匹配的分数无意义** | Alimeeting F1 0.06 不代表算法差，是任务定义差一个数量级 |
| **单一指标会误导** | 边界 F1 0.86 与聚类 F1 0.373 是两个维度，不可混谈 |
| **候选上限必须显式讨论** | 并查集合并的规模上限是实现者自选参数，应作为超参数对待 |
| **模型对比必须控制变量** | 对比必须固定输入、固定 max_tokens、控制思考开关，否则结论无效 |
| **负面结论要保留** | 1.3 复核在基础切分好时降分——这个结论比“多级流水线更强”更有价值 |
