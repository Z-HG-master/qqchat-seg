# 流水线总览

> 适用：把一个聊天群（或其它多人群聊语料）的消息流，加工成**纯文本的连续对话片段**，
> 供后续微调 / 检索 / 分析使用。
> 设计原则：**换群只改配置，流程不变**；每一步都有产物校验与断点续跑。

---

## 一、最终产出是什么

```
<data_root>/groups/<群号>_<群名>/segments_ctx.jsonl
```

每个事件一条，`messages` 是纯文本消息列表（图片已被转成文字描述）：

```json
{"event_id": "L0123", "peer": "123456789",
 "ts_first": 1788190689, "ts_last": 1788190900,
 "participants": ["示例用户A", "示例用户B"], "n_units": 7, "n_msgs": 7, "chars": 640,
 "messages": [
   "示例用户A: 这耳机续航有点猛",
   "示例用户B: [图片：一张表情包，画面为戴眼镜男子开怀大笑并指向右侧，用于表达调侃或捧场]",
   "示例用户A: 上周三开始用 用到现在，平均每天10小时 还有电"
 ]}
```

## 二、流水线总览

| 步骤 | 做什么 | 需要模型 | 产物 | 参考耗时* |
|---|---|---|---|---|
| **0.1** | 导入用户已导出的 `messages.jsonl`、补媒体占位、名字表 | — | `messages.jsonl` | 秒级 |
| **0.5** | 媒体转文本（图片约 50 字 / 表情 ≤15 字） | 小模型（视觉） | `messages_media.jsonl` | 9.8 min |
| **0.6** | 同人连发 → 语义分块 → 合并成 unit | 小模型 | `units.jsonl` | 2.5 min |
| **0.7** | @ 与 reply 语义初审（相关→建链接，不相关→删标记） | 小模型 | `units_at.jsonl` | 1 min |
| **0.8** | 文本卫生、悬空链接修正、空正文丢弃 | — | `units_at.jsonl` + `units_stats.json` | 秒级 |
| **1.1** | 事件判别（逐条 + 外延 5 段 + 带解释） | 小模型 | `s1_events_ev.jsonl` | 28.3 min |
| **1.2** | 按已确认的 @/reply 链接合并事件（非连续，≤20 条 / ≤2000 字） | — | `s1_events_linked.jsonl` | 秒级 |
| **1.3** | 长事件复核（>10 条，可递归切分） | 大模型 | `s1_events_reviewed.jsonl` | 5.1 min |
| **1.4** | 质量闸门（统一丢弃：单条 + 文字含量 <30，媒体按 15 字计） | — | `s1_events_gated.jsonl` | 秒级 |
| **1.5** | 事件级导出 + 规则分类 | — | `dataset_dataset.jsonl` / `catalog_dataset.jsonl` | 秒级 |
| **2.1** | 图片结合上下文重述（每图一次，两行输出） | 大模型（视觉） | `media_context_ctx.jsonl` | 21.6 min |
| **2.2** | 回填新描述 → 纯文本连续片段 | — | `segments_ctx.jsonl` | 秒级 |

\* 参考耗时来自一个约 6,600 条消息、815 张图片的中型群（本地 GPU，小模型 9B / 大模型 27B 量级），
用于成本量级估算，不同硬件差异很大。

**全流程约 70 分钟 / 群**。一条命令跑完：

```bash
python pipeline.py --group 123456789
python pipeline.py --status                   # 看各步产物
python pipeline.py --from 1.3 --to 2.2        # 断点续跑
python pipeline.py --list-prompts             # 打印全部提示词
```

“小模型 / 大模型”只是角色名，具体模型完全由 `config.json` 的
`model_small` / `model_big` 决定，任何 OpenAI 兼容端点上的模型都可以。

## 三、关键设计决策（含理由）

### 1. 为什么 unit = 同人连发合并，而不是单条消息
群聊里一个人常连发 3–5 条说完一件事。按单条处理会把一句话切成碎片。
合并后再让模型判语义分块（0.6），得到“语义单一的一条伪消息”。

### 2. 为什么 @ 和 reply 都要“初审”
实测 reply 边里相当大比例（约 48%）说的不是同一件事（“回复了你但聊别的”）。所以：
- @ 与 reply 都先做相关性判定（0.7）；
- 只有判为相关才建立 `reply_to_unit` 链接，后续才允许据此合并；
- 这也顺带把“@ 了但说别的”的假关联过滤掉了。

### 3. 为什么事件判别用“逐条 + 外延 5”，而不用窗口切分
两种都试过，最终选逐条是因为：
- 窗口版边界由“必须全覆盖”驱动，长事件会被 stride 硬切；
- 逐条版更贴近人读对话的方式（一条条看要不要另起一事）；
- **关键是要带解释**：模型输出“判定 + 理由”时准确率显著高于只输出一个字。

### 4. 为什么长事件要复核
小模型判完仍有少量 ≥21 条的长事件，其中混着“先聊游戏剧情、后聊比赛解说”这类跨话题。

⚠️ 但要注意：**当基础切分已经较好时，1.3 复核会降低分数**（公开基准上
F1 0.862 → 0.810）。这不是“多级复核提升质量”的流水线，默认保留它只是为了处理
长尾的长事件，可以按需跳过。

### 5. 为什么质量闸门放在最后
早期把“剔单条”放在复核前，结果复核把长事件切开又产生新的单条碎片。
统一放到最后只丢一次。

### 6. 为什么图片要两遍识别
- 第一遍（0.5）：**无上下文**，只看图本身 → 用于阶段 0/1 的文本替换与事件判别；
- 第二遍（2.1）：**带事件上下文**，能说出“这张图在回应什么” → 用于最终数据集。
两遍互补：第一遍敢写专有名词，第二遍擅长语境。

### 7. 为什么第二遍用“描述 + 关联”两行
单行时模型会把上下文塞进描述（“配合某某的调侃”），实测污染率 15–30%。
拆成两行后：描述只讲图（污染 0/20），关联专讲与对话的关系。

## 四、提示词

全部提示词的逐字存档见 [`prompts/PROMPTS.md`](../prompts/PROMPTS.md)（共 7 条）。要点：

| 阶段 | 提示词要点 |
|---|---|
| 0.5 图片 | 判断种类 + 50 字描述（画面/文字/数字/意图），只输出一行 |
| 0.5 表情 | 不超过 15 字，描述内容 + 情绪 |
| 0.6 分块 | 同人连发切成语义块，只输出区间 `1-2,3,4-5` |
| 0.7 初审 | 被 @/回复的人此前那条 vs 现在这条，是否相关，只答 YES/NO |
| 1.1 判别 | 逐条判「续/新」+ 一句话理由 |
| 1.3 复核 | 整段是否“逻辑顺畅、适合作为训练数据”，输出 结论/转折点/理由 |
| 2.1 重识别 | 「描述」（≤80 字，只讲图）+「关联」（与对话的关系）两行 |

**统一调用参数**：`temperature=0.1`（判別）/ `0.0`（基准测试）、单条 user 消息（无 system message）。

> **本流程不依赖思考模式（reasoning / thinking）。**
> 需要模型「多想一步」的地方，我们靠**提示词要求它输出一句理由**，而不是打开模型的思考模式：
> 前者只多几十个输出 token、单次仍是秒级；后者会消耗成百上千推理 token，实测单次从 0.9 秒
> 涨到 5–32 秒，小模型还常被截断。1.1 的「判定 + 一句理由」就是按这个思路设计的。
>
> 部分模型家族（如 Qwen）有 `reasoning_effort` 之类的私有旋钮；本项目**默认不发送该字段**，
> 也不把它当作设计前提。如果你的模型默认开思考拖慢速度，可在 config.json 里显式关掉（可选）。

## 六、换群 / 换数据的操作

1. 用你自己的工具把聊天记录**合法导出**成 `messages.jsonl`（每行一条，格式见 README）；
2. 放到 `<data_root>/groups/<群号>_<群名>/input/messages.jsonl`；
3. 在 `config.json` 里填 `group_id` / `group_name`（或运行时 `--group`）；
4. `python pipeline.py --group <群号>`；
5. `python pipeline.py --status` 全 ✓ 即完成，`segments_ctx.jsonl` 就是成果。

需要按群调整的参数（都有命令行参数，默认值见 `pipeline.py` 的 `STEPS`）：

| 参数 | 默认 | 何时调 |
|---|---|---|
| `--min-substance 30` | 事件文字含量下限（媒体按 15 字计） | 群特别大、想要精品时提高到 40–50 |
| `--max-units 20 --max-chars 2000` | 合并规模上限 | 群聊密度高时调小；**不要去掉上限** |
| `--min 10`（复核触发） | 超过 10 条才复核 | 想更严可降到 6；主切分好时可跳过 1.3 |
| `--lookahead 5` | 判“新”后向后看 5 条 | 一般不动 |

注意：20 条 / 2000 字是**在 IRC 数据上扫描出的值**，没有在真实群聊数据上扫描过
（见验证报告 §2.6）；质量闸门阈值 30 字同样未经数据验证。

## 七、已知局限

1. **人物名未被脱敏**：训练文本里是群友昵称。若下游需要 `user` 这类通用角色名，
   需在 2.2 之后再做一个映射层。
2. **跨事件的引用关系可能丢失**：合并只对“已确认链接”且规模受限的生效，
   远距离 reply 仍可能跨事件。
3. **长事件仍可能残存跨话题**：复核判“顺畅”但人工看可能仍有转折。
4. **图片描述是“转述”不是“原文”**：图片里的文字经视觉模型识别，可能有错字。
5. **未做去重**：群聊复读、转发同一内容仍会保留多份。
6. **真实群聊上没有人工标注的准确率**：公开基准只验证了 1.1 单步，
   真实场景的准确率未知。

更完整的验证数据与负面结论见 [`docs/validation-report.md`](validation-report.md)。
踩坑记录见 [`docs/pitfalls.md`](pitfalls.md)。
